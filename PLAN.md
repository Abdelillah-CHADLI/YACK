You are working on a software system consisting of three repositories:

1. Flutter mobile application
2. Node.js/Express backend
3. Admin dashboard

A previous forensic audit has already been completed. Two files exist:

* `FIXES.md` or `FIXED.md` — the audit findings and identified problems
* `SYSTEM_DOCUMENTATION.md` — documentation of the current system architecture and behavior

Your task is now to **systematically remediate the system until every actionable finding has been addressed, verified, tested, and re-audited**.

This is NOT a task where you read the report and blindly apply fixes one after another.

For every issue, you must follow this lifecycle:

`Understand -> Verify -> Plan -> Fix -> Review -> Test -> Integration Test -> Re-audit -> Mark Complete`

Do not consider an issue fixed merely because code was changed.

---

# 1. Primary objective

Resolve every legitimate actionable issue documented in the audit while preserving existing intended functionality across all three repositories.

The final system should:

* preserve existing business logic unless that logic is itself defective
* preserve working functionality
* maintain compatibility between mobile, backend, and admin
* avoid introducing regressions
* remove or correct security vulnerabilities
* fix frontend/backend mismatches
* fix data-model inconsistencies
* fix race conditions and unsafe concurrent operations
* remove leaked/hardcoded secrets where applicable
* improve validation and authorization
* fix error handling
* fix production configuration problems
* remove confirmed dead/unnecessary code
* fix reliability problems
* address realistic abuse cases
* improve test coverage around corrected behavior
* leave the repositories in a clean, internally consistent state

Do not redesign the application or perform unrelated refactoring.

---

# 2. Treat the audit as leads, not absolute truth

`FIXES.md` / `FIXED.md` was generated by another model.

Therefore:

**DO NOT blindly trust every finding.**

Before modifying code for an issue:

1. Read the finding.
2. Locate every referenced file.
3. Inspect the surrounding implementation.
4. Trace the complete execution path.
5. Inspect middleware and shared utilities.
6. Check related implementations in the other repositories.
7. Determine whether the issue still exists.
8. Determine whether the proposed fix is actually appropriate.
9. Check whether fixing it could break another workflow.

If the finding is incorrect, obsolete, already fixed, or based on a misunderstanding:

* do not introduce unnecessary changes
* mark it as `Not Reproducible`, `Already Fixed`, or `Invalid Finding`
* document the evidence

The audit report guides investigation. The source code remains the source of truth.

# 7. Required workflow for EVERY issue

For each issue:

## Step 1: Investigate

Reproduce or statically verify the issue.

Trace the relevant code.

Example:

If the report claims:

> Missing authorization on endpoint X

Do not immediately add middleware.

Check:

`route -> global middleware -> route middleware -> controller -> service -> database`

Authorization may already exist elsewhere.

---

## Step 2: Determine root cause

Fix the underlying cause, not only the symptom.

Example:

Bad:

```text
Frontend crashes because backend occasionally omits status
-> add null check
```

Better:

Determine why the API contract allows inconsistent status values and correct the contract where appropriate.

---

## Step 3: Determine blast radius

Before editing, search all usages of:

* changed functions
* changed models
* changed fields
* changed endpoints
* changed enums
* changed environment variables
* changed database structures

Check all three repositories.

---

## Step 4: Implement minimal correct fix

Prefer the smallest change that fully resolves the root cause.

Do not introduce unnecessary architectural rewrites.

---

## Step 5: Review your own change

Immediately inspect the diff.

Check for:

* accidental behavior changes
* missing imports
* incorrect types
* formatting problems
* nullability problems
* broken callers
* duplicated logic
* changed API contracts
* security regressions

---

## Step 6: Add/update tests

Every significant bug fix should have a regression test where reasonably possible.

A regression test should:

1. fail before the fix
2. pass after the fix

Prioritize tests for:

* security
* authentication
* authorization
* state transitions
* concurrency
* database consistency
* API contracts
* crypto
* validation
* critical user workflows

---

## Step 7: Run relevant tests

Run the smallest relevant test suite first.

Then run the repository's broader suite.

Examples:

Backend:

```text
unit tests
integration tests
lint
type/static checks if available
```

Flutter:

```text
flutter analyze
flutter test
```

Admin:

```text
lint
typecheck
tests
production build
```

Use the actual commands defined by each repository.

Do not assume commands without inspecting configuration.

---

## Step 8: Cross-repository verification

If the change affects an API, model, authentication behavior, notification, configuration, or shared workflow, verify the corresponding code in all affected repositories.

---

## Step 9: Re-audit the issue

After tests pass, inspect the implementation again as if reviewing another developer's patch.

Ask:

* Is the original vulnerability actually impossible now?
* Can the validation be bypassed?
* Does another endpoint expose the same problem?
* Did the fix merely move the bug?
* Did it create another race condition?
* Does the frontend correctly handle the new behavior?
* Does production configuration support it?

Only then mark the issue `Complete`.

# 8. Security fixes require adversarial verification

For security findings, test the fix from an attacker's perspective.

Where relevant test:

* missing token
* invalid token
* expired/revoked token
* another user's resource ID
* admin endpoint as normal user
* modified request payload
* unexpected fields
* malformed ObjectId
* oversized body
* invalid Base64
* invalid MIME type
* duplicate request
* replayed request
* concurrent requests
* excessive requests
* malicious filenames
* unsupported status transitions

Do not declare a security issue fixed merely because middleware was added.

---

# 9. Concurrency fixes

For every race-condition finding, explicitly reason about simultaneous requests.

Test cases should include scenarios such as:

```text
Request A ─┐
           ├── same resource
Request B ─┘
```

Verify that the final state is deterministic and valid.

Prefer:

* atomic database operations
* conditional updates
* unique constraints
* transactions where genuinely required
* idempotency

over application-level:

```text
read -> check -> modify -> save
```

when concurrency can invalidate the check.

# 14. Crypto-related findings

# 16. Do not blindly implement recommendations

Some items in the audit may be recommendations rather than bugs.

Distinguish:

### Defect

Existing behavior is incorrect.

Fix it.

### Security issue

Existing behavior creates an exploitable weakness.

Fix it.

### Reliability issue

Existing behavior can realistically fail.

Fix it.

### Technical debt

Safe improvement with no immediate correctness impact.

Fix only after higher priorities.

### Feature request / future work

New functionality not required for correctness.

Do NOT automatically implement it.

Mark:

`Out of Scope - Feature Enhancement`

unless it is required to resolve another confirmed issue.

# Critical operating rules

1. Never mark something fixed without verifying the resulting behavior.

2. Never trust the original audit blindly.

3. Never modify one repository's API contract without checking its consumers.

4. Never introduce breaking database or crypto changes without considering existing production data.

5. Never expose secrets in output.

6. Never replace working business logic unnecessarily.

7. Never perform broad refactors unrelated to an identified problem.

8. Never skip tests because a change "looks correct."

9. Never stop after implementing the original findings. Perform a fresh audit afterward.

10. When tests expose another defect, investigate the root cause rather than modifying the test to make it pass.

11. Do not weaken security checks or validation simply to restore compatibility.

12. Do not suppress lint/type/compiler errors without understanding them.

13. Do not use placeholder implementations to mark an issue complete.

14. Do not silently ignore issues you cannot fix.

15. Source code and verified runtime behavior are the final source of truth.

Begin by reading `FIXES.md`/`FIXED.md` and `SYSTEM_DOCUMENTATION.md`, mapping the three repositories, checking the current git state, and constructing `REMEDIATION.md`.

Do not begin modifying production code until the remediation tracker and dependency/priority order have been established.
